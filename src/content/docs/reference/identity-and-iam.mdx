This page is the reference for the IAM surface of a cyoda-go deployment in
JWT mode (`CYODA_IAM_MODE=jwt`). It covers how tokens are issued, which
endpoints manage clients and keys, and which settings govern them. For the
model behind it, see
[Authentication and identity](/concepts/authentication-and-identity/). For
an application team's step-by-step integration, see
[Authenticating your application](/build/authenticating-applications/).

Paths below are relative to `CYODA_CONTEXT_PATH` (`/api` by default). The
[REST API reference](/reference/api/) carries the authoritative request and
response schemas. The help topics [`auth tokens`](/help/auth/tokens/),
[`auth clients`](/help/auth/clients/) and
[`auth trusted-keys`](/help/auth/trusted-keys/) list every error case.

## Authorization tiers

| Tier | Token | Reaches |
| --- | --- | --- |
| Data | Any token with `ROLE_M2M`: plain, admin and on-behalf-of clients | Every data operation over HTTP and gRPC in the token's tenant, model and workflow import included |
| Tenant admin | `ROLE_ADMIN` in the tenant, not from a token exchange | `/clients*` and `/oauth/keys/trusted*` |
| Platform operator | `ROLE_ADMIN` in the tenant `PLATFORM`, not from a token exchange | `/oauth/keys/keypair*`, `POST /platform/clock`, `GET /platform/cluster`, `/admin/*` |

`GET /account` and `GET /platform/clock` need only a valid token. The token
endpoint, `GET /.well-known/jwks.json`, `GET /health` and the gRPC health
`Check` take no bearer token. A token that lacks the required role gets
`403 FORBIDDEN` (gRPC `PermissionDenied`) before the operation runs. A token
from a token exchange never administers, whatever its roles.

## Token endpoint

`POST /api/tenants/{tenant}/oauth/token`, where `{tenant}` is the client's
tenant. The request body is `application/x-www-form-urlencoded`. The client
authenticates with HTTP Basic only (`client_secret_basic`). A `client_id` and
`client_secret` sent as form fields are not read and answer
`401 invalid_client`. The endpoint takes no query parameters.

| Grant | `grant_type` | Client | Extra form fields |
| --- | --- | --- | --- |
| Client credentials | `client_credentials` | Plain or admin | none |
| Token exchange (RFC 8693) | `urn:ietf:params:oauth:grant-type:token-exchange` | On-behalf-of | `subject_token`, `subject_token_type=urn:ietf:params:oauth:token-type:jwt` |

A `client_credentials` response:

```json
{"access_token":"eyJhbGciOiJSUzI1NiIs…","expires_in":300,"token_type":"Bearer"}
```

A token exchange adds `"issued_token_type":"urn:ietf:params:oauth:token-type:jwt"`.
`expires_in` is the token's remaining life: at most `CYODA_JWT_EXPIRY_SECONDS`
(default 300). For an exchange, it is also capped by the assertion's `exp`.
There is no refresh token and no `scope`. Fetch a new token when less than
about 60 seconds remain.

Errors use the OAuth shape `{"error": "…", "error_description": "…"}`, and
every `error_description` is a fixed string. The endpoint changes nothing, so
a retry is always safe. These are the ones to handle in code:

| Status and `error` | Meaning | Retry? |
| --- | --- | --- |
| `401 invalid_client` | No Basic header, unknown tenant or client, wrong secret | Re-read the credentials once, then stop |
| `400 unauthorized_client` | Wrong grant for the client kind | No |
| `400 invalid_request` | Malformed request, or an assertion refused (bad key, signature, claims or `sub`) | Only `subject token claims rejected` and `subject token has expired`, once, with a fresh assertion |
| `403 access_denied` | The assertion's `caas_org_id` is not the client's tenant | No |
| `429 slow_down` | The client used its `CYODA_IAM_TOKEN_REQUESTS_PER_MINUTE` on this node | After `Retry-After` |
| `503 temporarily_unavailable` | Store unreadable, or no secret-check slot within 1 second | After `Retry-After`, with backoff |
| `500 server_error` | Store failure, damaged client record or signing failure; carries a ticket | A few times with backoff |

<Aside type="caution" title="Rate-limit the token endpoint at ingress">
Each request with an unknown client or a wrong secret costs one bcrypt check
and holds its connection for a 500 ms response floor. cyoda-go bounds that
work per node and then answers `503`, so a flood of bad credentials can keep
legitimate clients out. The per-client limit counts only after a client
authenticates. Put a per-source rate limit in front of the path
`^/api/tenants/[^/]+/oauth/token$` at the ingress, gateway or load balancer.
</Aside>

`GET /api/.well-known/jwks.json` is the JWK Set of cyoda-go's signing keys,
served without authentication. Applications do not need it to call cyoda-go,
but they can use it to verify a token themselves.

## First admin token

No credential is defined by configuration except the signing key. The
platform operator signs the first admin token offline with `cyoda token`, on
any host or container that holds `CYODA_JWT_SIGNING_KEY`. The command opens
no store and makes no network call.

```bash
TOKEN=$(cyoda token --tenant acme)                          # ROLE_ADMIN in acme
TOKEN=$(cyoda token --tenant acme --roles ROLE_ADMIN,ROLE_M2M)  # also reaches data
TOKEN=$(cyoda token --tenant PLATFORM)                      # platform operator
```

The token names a person (`user_roles`, kind `user`), whose id is `--user`
(default `operator`). Its lifetime is `--ttl`, at most
`CYODA_JWT_EXPIRY_SECONDS`. It never opens a compute-node stream. It verifies
for as long as the signing key does: a key-pair rotation does not end it, but
invalidating or deleting the bootstrap key does. Flags, exit codes and
the revocation procedure are in [`cyoda help cli token`](/help/cli/token/).

## Machine-to-machine clients

Requires `ROLE_ADMIN`. A client belongs to the caller's tenant.

| Method and path | Purpose |
| --- | --- |
| `GET /clients` | List the tenant's clients, sorted by `clientId`. Never returns a secret. |
| `POST /clients` | Create a client. No body; query parameters `clientId`, `withAdminRole`, `onBehalfOf`. |
| `PUT /clients/{clientId}/secret` | Reset the secret. The old secret stops working at once on every node. |
| `DELETE /clients/{clientId}` | Delete the client. Its tokens stay valid until their `exp`. |

Every client receives `ROLE_M2M`. `withAdminRole=true` adds `ROLE_ADMIN` and
needs `CYODA_IAM_M2M_ADMIN_ROLE_ENABLED=true` on the node that takes the call
(otherwise `404 FEATURE_DISABLED`). `onBehalfOf=true` creates an on-behalf-of
client. That flag is immutable, cannot be combined with `withAdminRole=true`,
and is refused in the `PLATFORM` tenant (`400 BAD_REQUEST` in both cases).
Without `clientId`, a 16-character id is generated.

The creation (and reset) response is shown once:

```json
{
  "client_id": "backend-obo",
  "client_secret": "de95…(64 lower-case hex characters)…d548",
  "client_secret_expires_at": 0,
  "grant_type": "urn:ietf:params:oauth:grant-type:token-exchange",
  "onBehalfOf": true,
  "roles": ["ROLE_M2M"]
}
```

A list item carries `clientId`, `creationDate`, `lastUpdateDate`, `roles` and
`onBehalfOf`. A taken id answers `409 M2M_CLIENT_EXISTS`. A tenant at
`CYODA_IAM_M2M_CLIENT_MAX_PER_TENANT` clients answers
`400 M2M_CLIENT_CAP_REACHED`. Clients live in the cluster's store, so a
create, reset or delete is in force on every node when the call returns. A
compute-node stream opened with a deleted or reset client closes within 60
seconds.

## Trusted keys

Requires `ROLE_ADMIN` and `CYODA_IAM_TRUSTED_KEY_REGISTRATION_ENABLED=true` on
every node (otherwise `404 FEATURE_DISABLED`). A trusted key is an RSA public
key whose private half an application uses to sign user assertions. It
verifies only the subject token of a token exchange. It is never checked on
an API call.

| Method and path | Purpose |
| --- | --- |
| `GET /oauth/keys/trusted` | List the tenant's keys with status and validity window. |
| `POST /oauth/keys/trusted` | Register a key, or replace the key with the same `keyId`. |
| `POST /oauth/keys/trusted/{keyId}/invalidate` | Stop accepting assertions signed with it, at once. No request body. |
| `POST /oauth/keys/trusted/{keyId}/reactivate` | Re-enable it. Body: `validTo` (required), `validFrom`. |
| `DELETE /oauth/keys/trusted/{keyId}` | Remove it. |

A registration takes `keyId` and `jwk`, with optional `issuers`, `validFrom`,
`validTo` and `invalidatePrevious`:

```json
{
  "keyId": "backend-key-2026-11",
  "jwk": { "kty": "RSA", "n": "xZyEjnejDeuM…", "e": "AQAB", "alg": "RS256", "use": "sig" }
}
```

- `keyId` matches `^[A-Za-z0-9._-]{1,128}$` and becomes the `kid` the
  application signs with. Key ids are unique per tenant: two tenants can each
  register the same id.
- `kty` must be `RSA`, with a 2048- to 4096-bit modulus. A JWK carrying a
  private member (`d`, `p`, `q`, …) is refused. Only `kty`, `kid`, `n`, `e`,
  `alg` and `use` are stored.
- Without `validTo`, a key is valid for
  `CYODA_IAM_TRUSTED_KEY_MAX_VALIDITY_DAYS` (365) days. After `validTo`, every
  exchange with it fails, although the list still shows `active: true`.
- Trusted keys have no grace period and no audience. An invalidated key frees
  its slot under `CYODA_IAM_TRUSTED_KEY_MAX_PER_TENANT` (10) at once.
- A key belongs to the tenant, not to a client. Any on-behalf-of client of the
  tenant can exchange an assertion signed with any active key of the tenant.

## Signing key pairs

Requires a platform operator. cyoda-go signs every token with RS256. The
bootstrap key, derived from `CYODA_JWT_SIGNING_KEY`, signs until the operator
issues other key pairs. Its key id is the same on every node that shares the
PEM.

| Method and path | Purpose |
| --- | --- |
| `GET /oauth/keys/keypair/current` | The key pair that signs now (public part). |
| `POST /oauth/keys/keypair` | Issue a key pair (`algorithm: RS256`), optionally invalidating the current ones. |
| `POST /oauth/keys/keypair/{keyId}/invalidate` | Invalidate it, with an optional `gracePeriodSec`. |
| `POST /oauth/keys/keypair/{keyId}/reactivate` | Reactivate it. |
| `DELETE /oauth/keys/keypair/{keyId}` | Delete it. |

- Of the active key pairs inside their validity window, the one with the
  latest `validFrom` signs. A key pair verifies only inside its window.
- A key pair has no audience. A grace period (`gracePeriodSec`, or
  `invalidateGracePeriodSec` on a rotation) is at most 3600 seconds, the
  longest token lifetime. A larger value is `400 BAD_REQUEST`.
- A rotation with `invalidateCurrent: true` invalidates the issued key pairs
  only. The bootstrap key stays active and `cyoda token` keeps working. Only
  an invalidate or delete that names the bootstrap key's id ends it.
- Key pairs are stored and shared by the cluster, and survive restarts on
  SQLite and PostgreSQL. A node that cannot reconcile its key copy for ten
  intervals of `CYODA_AUTH_CACHE_RECONCILE_INTERVAL` refuses every token
  rather than serve a stale answer.
- To end a leaked token, revoke the key pair named by the `kid` in its
  header. A rotation is not enough.

Rotation, emergency revocation and recovery procedures are in
[`cyoda help config auth`](/help/config/auth/).

## Identifiers

| Identifier | Rule | Reserved |
| --- | --- | --- |
| Tenant id | `^[A-Za-z0-9][A-Za-z0-9._-]{0,99}$`, case significant | `SYSTEM` in any letter case |
| Client id | Same grammar, unique within its tenant | `system` in any letter case |
| User id | Valid UTF-8, 1 to 255 characters, no control character, noncharacter or U+FFFD; never normalised | `system` in any letter case |

Tenant ids appear in URLs and gateway logs: put no personal data or secret in
one. A token whose `caas_org_id` or user claim breaks its rule is refused with
`401`.

## Configuration

The settings below govern IAM. The full list, with defaults, is under
[Configuration → auth](/reference/configuration/#vars-auth).

| Variable | Default | Effect |
| --- | --- | --- |
| `CYODA_IAM_MODE` | `mock` | `mock` or `jwt`. Any other value fails startup. |
| `CYODA_REQUIRE_JWT` | `false` | Refuse to start unless JWT mode and a signing key are configured. |
| `CYODA_IAM_MOCK_KIND` | `service` | Mock mode: kind of the fixed principal (`user`, `service`, `system`). |
| `CYODA_IAM_MOCK_ROLES` | `ROLE_ADMIN,ROLE_M2M` | Mock mode: roles of the fixed principal. |
| `CYODA_JWT_SIGNING_KEY` (`_FILE`) | none | RSA private key, PEM or base64 PEM. The root secret. |
| `CYODA_JWT_ISSUER` | `cyoda` | `iss` of every token; the `aud` a user assertion must carry. |
| `CYODA_JWT_AUDIENCE` | empty | When set, required `aud` on inbound tokens and set on issued ones. |
| `CYODA_JWT_EXPIRY_SECONDS` | `300` | Token lifetime, 1 to 3600. |
| `CYODA_IAM_M2M_ADMIN_ROLE_ENABLED` | `false` | Allows `POST /clients?withAdminRole=true`. |
| `CYODA_IAM_M2M_CLIENT_MAX_PER_TENANT` | `100` | Client cap per tenant; `0` is unbounded. |
| `CYODA_IAM_TOKEN_REQUESTS_PER_MINUTE` | `600` | Token requests per client per node; `0` is unlimited. |
| `CYODA_IAM_TOKEN_MAX_CONCURRENT_SECRET_CHECKS` | CPUs | Concurrent bcrypt checks per node. |
| `CYODA_IAM_TRUSTED_KEY_REGISTRATION_ENABLED` | `false` | Enables the trusted-key endpoints. |
| `CYODA_IAM_TRUSTED_KEY_MAX_PER_TENANT` | `10` | Active trusted keys per tenant. |
| `CYODA_IAM_TRUSTED_KEY_MAX_VALIDITY_DAYS` | `365` | Validity of a key registered without `validTo`. |
| `CYODA_IAM_KEYPAIR_DEFAULT_VALIDITY_DAYS` | `365` | Validity of an issued key pair without `validTo`. |

The feature flags and limits are read by each node at startup, and the node
that takes a request decides by its own value. Give every node the same
values. The Helm chart has no dedicated values for them: set them with
`extraEnv`.
