cyoda-go ships with three storage engines: in-memory, SQLite and PostgreSQL.
They differ in durability, fault tolerance and operational footprint, but the
**application contract is identical across all of them.** Code written against
one runs unchanged against any other. `CYODA_STORAGE_BACKEND` selects the
engine at start (`memory`, `sqlite` or `postgres`).

Commercial storage backends are also available; for those, contact Cyoda.

## One application contract

Every engine offers the same isolation contract: **Snapshot Isolation with
First-Committer-Wins on entity-level conflicts** (SI+FCW).

What that gets you:

- **Snapshot reads** — a transaction sees a consistent view of the data as
  of its start, plus its own writes, regardless of concurrent writes.
- **Entity-level conflict detection at commit** — if another transaction
  committed a change to an entity you read or wrote, your transaction aborts
  at commit with a retryable `409 CONFLICT`.
- **First-committer-wins on write/write conflicts** — concurrent updates to
  the same entity resolve deterministically; the second commit aborts.

What it does **not** give you:

- **No phantom or predicate protection.** A transaction that counts entities
  matching a predicate cannot rely on the count being stable across the
  transaction's lifetime. Workflow logic that needs predicate-stable counts has
  to be expressed as an explicit serialization point — see the operational
  rule for workflow authors in
  [Concepts → Entities and lifecycle](/concepts/entities-and-lifecycle/).

The in-memory and SQLite engines implement SI+FCW in process. The PostgreSQL
engine runs every transaction under PostgreSQL `REPEATABLE READ` and adds
first-committer-wins validation of the transaction's read set at commit.

**A successful write is visible everywhere.** A `2xx` write response means that
the data is visible to every later read on every node. A caller can write and
then read its own data back.

Every engine also agrees on these details:

- Compare-and-save compares the expected transaction id literally, and refuses
  an empty one.
- A write inside a transaction carries that transaction's id.
- A point-in-time read inside a transaction is committed-only.
- Text comparisons order by byte value.
- A client disconnect stops the in-flight per-item work.

### Commit and consistency semantics

These hold on every engine:

- **A write is dated at its transaction's commit.** Every entity a transaction
  writes carries the same instant, taken immediately before the commit, so a
  point-in-time read sees all of a transaction's writes or none of them. A
  date sent on a write is ignored. Commit stamps strictly increase and never
  go back.
- **One version per entity per transaction.** However often a transaction
  writes an entity, it records one version of it, and the change history has
  one entry for that transaction.
- **Unique keys are checked at commit**, on the entities as the transaction
  leaves them, with the unique-key definitions of the stored model. Two
  entities of one transaction can swap key values; a duplicate refuses the
  commit with `409 UNIQUE_VIOLATION`.
- **A conditional delete is atomic.** Without `transactionSize` it is one
  transaction: any failure to delete one entity fails the whole request and
  deletes nothing. With `transactionSize`, each batch is atomic.
- **The consistency time fences point-in-time reads.**
  `GET /api/entity/consistency-time` returns the instant up to which no save of
  your tenant can still land. A read at or before it gives the same answer for
  ever; a `pointInTime` later than it is refused with
  `400 POINT_IN_TIME_AFTER_CONSISTENCY_TIME`. It covers every save confirmed
  on any node of a cluster, and it never goes back, also across a restart.

See [Consistent reads](/build/consistent-reads/) for how to use the
consistency time, and [`cyoda help crud`](/help/crud/) (POINT-IN-TIME
SEMANTICS) for the full rules.

## At a glance

| Engine | Durability | Fault tolerance | Scale envelope | Footprint | Best-fit scope |
|---|---|---|---|---|---|
| **In-memory** | Ephemeral | None — restart loses data | Bounded by host RAM | Single binary, no dependencies | Tests, digital-twin simulations |
| **SQLite** | Durable (single file) | Single process; survives restart, not disk loss | Single node, disk-bound | Single binary, no dependencies | Desktop, edge, single-node production |
| **PostgreSQL** | Durable, replicated by PostgreSQL | HA through PostgreSQL replication and failover; a transaction whose node is lost fails, and the client retries | Multi-node stateless cluster; writes bounded by the PostgreSQL primary | cyoda-go nodes + PostgreSQL 14+ (managed or self-hosted) | Multi-node production; audit and compliance |

All three ship with cyoda-go under the Apache 2.0 license.

## In-memory

The in-memory engine keeps all entity state in process memory. Transactions
complete in microseconds; there are no I/O paths and no external
dependencies. State is lost when the process exits.

It is the right choice for tests and for digital-twin simulations where
durability is delegated to a snapshot mechanism elsewhere. It is **not**
appropriate for any deployment where data must survive a restart.

A single process owns the store; there is no way to share in-memory state
across processes. Memory consumption is bounded by host RAM.

## SQLite

The SQLite engine gives you durable single-node storage with the same
zero-dependency footprint as in-memory: a single `cyoda` binary, a single
database file, no other moving parts. The driver is a pure-Go WASM build of
SQLite — no CGO, clean cross-compilation.

SQLite provides only database-level write locking; entity-level conflict
detection (SI+FCW) is layered on top by cyoda-go. The running process holds an
exclusive `flock` on the database file for its entire lifetime, so a second
process against the same file fails fast at startup with a clear error. Two
processes sharing a file would have independent SI+FCW state and silently
corrupt each other.

Best-fit deployments: desktop applications, edge devices, containerised
single-node production. The combination of "must survive restart" and "single
process is enough" lands here.

**Not** suitable for NFS-mounted database files (SQLite itself is unreliable on
NFS), nor for any deployment that needs more than one cyoda-go process against
the same data. If either of those applies, move to PostgreSQL.

SQLite migrations run when the node opens the database. `cyoda migrate` is a
no-op on SQLite.

### Size the reader pool against your memory limit

The SQLite engine opens a dedicated pool of read connections, so a long scan
does not block concurrent writes. `CYODA_SQLITE_READER_POOL_SIZE` sets the pool
size. It defaults to `GOMAXPROCS`, limited to the range 4 to 8.

Plan for the memory cost. `CYODA_SQLITE_CACHE_SIZE` (default `64000` KiB) is
**per connection**. The resident ceiling is therefore
`(readers + 1) × CYODA_SQLITE_CACHE_SIZE`. On an 8-CPU host with the default
values, that is approximately 562 MiB.

`GOMAXPROCS` follows the CPU quota, and it does not read the memory limit. In a
container with many cores and little memory, lower the pool size rather than
the cache size, which would shrink the writer's cache as well.

## PostgreSQL

The PostgreSQL engine is cyoda-go's production multi-node tier. A small
cluster of stateless cyoda-go nodes sits behind a load balancer with
PostgreSQL as the only stateful dependency. Cluster discovery is gossip-based
(HashiCorp `memberlist`, embedded); there is no ZooKeeper, etcd or Kafka to
operate. See [Cluster operations](/run/cluster-operations/).

PostgreSQL 14 or later is required. The engine works with managed PostgreSQL
platforms — RDS, Cloud SQL, Azure Database, Supabase, Neon, Aiven — or with
self-hosted PostgreSQL. Use the platform's direct-connection endpoint: a
PgBouncer in transaction-pooling mode (Supabase port 6543, Neon's pooled
endpoint) breaks the driver's prepared-statement cache.

Write throughput is bounded by the single PostgreSQL primary. The cluster
scales out for connection capacity and read fan-out, not for writes. Read
replicas are not used.

**Tenant isolation** is the `tenant_id` predicate that every statement
carries. The migrations create row-level security policies, but they take no
effect: cyoda-go connects as the owner of its tables, and the policies are not
forced. Running cyoda-go as a role that does not own the tables, or forcing
row-level security, is not supported.

**A transaction belongs to the node that opened it.** Its PostgreSQL
transaction lives on one connection of that node, and requests for it from
other nodes are proxied there. If that node dies mid-transaction, PostgreSQL
rolls the transaction back when the connection closes; the operation that
owned it fails and the client retries from scratch. A request that could not
reach the owner answers `503 TRANSACTION_NODE_UNAVAILABLE`. This is what lets
the engine run without a consensus protocol.

### Connection pools

Each node opens up to four PostgreSQL pools, so that entity transactions
cannot starve the scheduler or the model store:

| Pool | Size variable | Default | Used for |
|---|---|---|---|
| `main` | `CYODA_POSTGRES_MAX_CONNS` (and `CYODA_POSTGRES_MIN_CONNS`, default `5`) | `25` | Entity transactions and reads, search, `GET /scheduled-tasks` |
| `scheduler` | `CYODA_POSTGRES_SCHEDULER_CONNS` (at least `2`) | `10` | Scheduled-task claims and bookkeeping, the async-search heartbeat and claim |
| `heartbeat` | — | `1` | The scheduler heartbeat |
| `model` | `CYODA_POSTGRES_MODEL_CONNS` (at least `2`) | `8` | Model reads, schema extensions (at most half the pool), model administration |

That is up to **44 connections per node** at the defaults. Multiply by the
number of nodes and check the total against PostgreSQL's `max_connections`;
see [Cluster operations](/run/cluster-operations/#postgresql-connection-budget).
An invalid scheduler or model pool size stops the server at startup.

`cyoda.storage.pool.connections` reports every pool, labelled by `pool`
(`main`, `scheduler`, `heartbeat`, `model`). The other pool instruments,
exported as `cyoda_storage_pool_*` at `/metrics` and always on, cover the main
pool. `cyoda.storage.pool.empty_acquire_wait`, the time callers waited on an
empty main pool, is the saturation signal to alarm on. See
[`cyoda help telemetry`](/help/telemetry/).

### Ceilings and saturation

The engine sets five configurable ceilings on the database side. All five are
on by default. Each one takes a Go duration. Set a value to `0` to disable that
limit. A malformed value stops the server at startup.

| Variable | Default | Bounds |
|---|---|---|
| `CYODA_POSTGRES_STATEMENT_TIMEOUT` | `5m` | Any single statement |
| `CYODA_POSTGRES_IDLE_IN_TX_TIMEOUT` | `5m` | Idle gap inside an open transaction |
| `CYODA_POSTGRES_ACQUIRE_TIMEOUT` | `10s` | Waiting for a pooled connection when opening a transaction, or for a second connection inside one |
| `CYODA_POSTGRES_MIGRATE_LOCK_TIMEOUT` | `5m` | Lock waits on the migration connection |
| `CYODA_POSTGRES_SEARCH_STATEMENT_TIMEOUT` | `30m` | Async-search statements |

A compute-node callout holds its transaction's connection idle while it
waits, so the idle-in-transaction ceiling must clear the longest callout.
`responseTimeoutMs` is capped at `CYODA_CALLOUT_RESPONSE_TIMEOUT_MAX_MS`
(default `60s`), and the documented relation is
`(CYODA_RETRY_FIXED_NUM_RETRIES + 1) × CYODA_CALLOUT_RESPONSE_TIMEOUT_MAX_MS +
CYODA_DISPATCH_WAIT_TIMEOUT + CYODA_CALLOUT_HANDOVER_ALLOWANCE` under
`CYODA_POSTGRES_IDLE_IN_TX_TIMEOUT`: 275 seconds against 5 minutes at the
defaults. The server does not enforce it, so keep it when you raise any of
those values. The ceiling applies per idle gap, not per transaction.

Three conditions return a retryable **`503 STORAGE_UNAVAILABLE`**: the pool
could not supply a connection, the idle ceiling aborted the transaction, and
the connection went away. See
[`cyoda help errors STORAGE_UNAVAILABLE`](/help/errors/storage_unavailable/).

### Migrations and maintenance windows

Migrations are embedded in the binary. With `CYODA_POSTGRES_AUTO_MIGRATE=true`
(the default) a node applies them at start; nodes starting together take turns
under an advisory lock. `cyoda migrate` applies them as a separate step, which
is how the Helm chart runs them. A database newer than the binary is refused,
and a migration left dirty by a failure stops startup until it is recovered by
hand (see [`cyoda help cli migrate`](/help/cli/migrate/)).

Some migrations build indexes with a plain `CREATE INDEX` or alter a table
under a lock, and block traffic to those tables while they run. On a populated
database, plan a maintenance window for them:

| Migration | Blocks | Time grows with |
|---|---|---|
| `000008` | Writers to `entities` | Rows in `entities` |
| `000011` | Writers to `entities` for the index build; readers of `entities` for a moment at the swap | Rows in `entities` |
| `000012` | Writers to `entities` and `entity_versions` (readers are unaffected) | Rows in `entity_versions` and `entities` (full backfill and foreign-key validation) |
| `000013` | Writers to `sm_audit_events`, which includes every committing transaction | Rows in `sm_audit_events` |
| `000014` | Readers and writers of `scheduled_tasks` (table rewrite and five indexes) | Rows in `scheduled_tasks` (one per armed timer) |

Size one window to cover `000011` through `000014` together. `000016` reads
`entity_versions` once to set the starting consistency time; it blocks no
writer. For a large database, stop the cluster and run
`cyoda migrate --timeout <duration>` once, rather than relying on
auto-migration at start, which runs within `CYODA_STARTUP_TIMEOUT` (default
`30s`). See [Cluster operations](/run/cluster-operations/#upgrades).

## Choosing an engine

Match the engine to the operational shape you can sustain:

- **Local development and tests** — start on **in-memory**. Microsecond
  transactions, no setup, no cleanup.
- **Desktop, edge, single-node production** — **SQLite**. Durable, embedded,
  single binary.
- **Multi-node self-hosted production**, including audit and compliance
  workloads — **PostgreSQL**. Managed PostgreSQL keeps the operational
  footprint small.
- **Write throughput beyond a single PostgreSQL primary** — a commercial
  backend; contact Cyoda.

The progression is not a forced upgrade path; some deployments stay on SQLite
indefinitely, and that is the right answer for them. The application contract
does not change when you move. The
[growth-path framing in Concepts](/concepts/digital-twins-and-growth-path/)
covers the decision in narrative form.
