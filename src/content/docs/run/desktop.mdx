The desktop packaging is cyoda-go as it ships out of the box: a single
binary, no orchestrator, no external database. It is the right choice for
local development, edge deployments, small-team self-hosting, and any
low-volume production workload where a single machine is enough.

## In-memory vs SQLite

The desktop binary supports two storage modes:

- **In-memory** — everything lives in process memory. Sub-millisecond
  latencies. Data is lost on restart. Use it for tests, demos, and
  digital-twin scenario runs. This is what the binary runs on until it is
  given a configuration.
- **SQLite** — durable, single-file, zero-ops. Data survives restarts;
  backup is a file copy. Use it for everyday persistent work. SQLite is
  single-writer; all writes serialize through the database file, which
  limits concurrent write throughput.

SQLite is selected by a config file, not by default:

- `cyoda init` writes a user config (`~/.config/cyoda/cyoda.env`, or
  `%AppData%\cyoda\cyoda.env` on Windows) with `CYODA_STORAGE_BACKEND=sqlite`.
  The install script runs it for you; after Homebrew, a Windows archive or
  `go install`, run it yourself.
- The `.deb` and `.rpm` packages ship a system config,
  `/etc/cyoda/cyoda.env`, that selects SQLite. `cyoda init` then does nothing
  unless you pass `--force`.

The database file defaults to `~/.local/share/cyoda/cyoda.db` on Linux and
macOS and `%LocalAppData%\cyoda\cyoda.db` on Windows; `CYODA_SQLITE_PATH`
overrides it. Back it up by copying the file while the server is stopped:
the database runs in WAL mode, so a copy of the main file taken while the
server runs can miss recent writes. Migrate it by moving the file.

## Install

See [Install](/run/install/) for every route — Homebrew, the signed install
script, `.deb` and `.rpm` packages, Windows and `go install` — and how to
verify each. On macOS or Linux with Homebrew:

```bash
brew install cyoda/cyoda-go/cyoda
cyoda init
```

## Run

```bash
cyoda
```

`cyoda serve` is the same command. It takes no flags: any argument other than
`-h` / `--help` is refused with exit code `2` before anything starts. The full
CLI reference lives at [Reference → CLI](/reference/cli/).

The server opens three listeners, all bound to `127.0.0.1` by default:

| Listener | Port | Bind address variable | Serves |
|---|---|---|---|
| REST API | `8080` (`CYODA_HTTP_PORT`) | `CYODA_HTTP_BIND_ADDRESS` | Every API endpoint under `/api` |
| gRPC | `9090` (`CYODA_GRPC_PORT`) | `CYODA_GRPC_BIND_ADDRESS` | Compute nodes, gRPC entity API |
| Admin | `9091` (`CYODA_ADMIN_PORT`) | `CYODA_ADMIN_BIND_ADDRESS` | `/livez`, `/readyz`, `/metrics` |

On loopback, only processes on the same host reach the server. To serve
clients or compute nodes on other hosts, set the bind addresses to `0.0.0.0`
(or `::`) — and switch to JWT mode first.

<Aside type="caution" title="Mock auth is the default">
The default IAM mode is `mock`: every caller acts as one admin principal with
data access. The server logs a WARN when a mock-mode HTTP or gRPC listener is
bound to an address other than loopback. Before you bind to a network, set
`CYODA_IAM_MODE=jwt` and a signing key; see
[Authenticating applications](/build/authenticating-applications/).
</Aside>

`cyoda health` checks readiness from the same host: it calls `/readyz` on the
admin port and exits `0` when the node is ready, `1` otherwise. Use it in a
process supervisor's health check. No systemd units ship with cyoda-go;
supervising the process is up to you.

`Ctrl+C` (or `SIGTERM`) shuts the server down gracefully: running scheduled
work drains first, then in-flight requests. A second signal during the drain
forces an immediate exit with code `2`. For the drain timings, see
[Cluster operations](/run/cluster-operations/).

## Configure

cyoda-go reads configuration from `CYODA_*` environment variables and from
env files: the system config, the user config written by `cyoda init`,
`./.env`, and the profile files `CYODA_PROFILES` selects. There are no
configuration flags. The full list of options and the precedence rules live
at [Reference → Configuration](/reference/configuration/); for everyday use
the defaults are fine, and you set only a handful of variables
(`CYODA_STORAGE_BACKEND`, ports and bind addresses, the JWT signing key).

For secrets, the credential variables (`CYODA_JWT_SIGNING_KEY`,
`CYODA_HMAC_SECRET`, `CYODA_POSTGRES_URL`, `CYODA_METRICS_BEARER`) each take a
`*_FILE` companion that reads the value from a file, so the secret stays off
the command line and out of the process environment.

In JWT mode, the first admin token comes from the binary itself:
`cyoda token --tenant <tenant>`, run in the same environment as the server, signs
it with the server's signing key. See
[`cyoda help cli token`](/help/cli/token/).

## Upgrading

Read the [release notes](/releases/v0-9-0/) for the target release, then
install the newer release by the route you used before and restart the
process. The SQLite schema migrates when the new binary starts. See
[Install → Upgrade](/run/install/#upgrade).
