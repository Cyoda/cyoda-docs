Kubernetes is the production packaging for self-hosted cyoda-go. The Helm
chart that ships with cyoda-go runs a StatefulSet of identical, stateless
cyoda-go pods against an external PostgreSQL database, which is the only
stateful dependency. This page covers the deployment shape, installation, the
first admin token, upgrades and sizing. [Cluster operations](/run/cluster-operations/)
covers what applies to any cluster, and [Helm values](/reference/helm/) covers
the chart's values.

## Deployment shape

```
        Gateway (HTTPRoute :8080, GRPCRoute :9090) or Ingress
                              │
                 Service cyoda (ClusterIP: 8080, 9090, 9091)
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
   ┌────▼────┐           ┌────▼────┐           ┌────▼────┐
   │ cyoda-0 │◄─────────►│ cyoda-1 │◄─────────►│ cyoda-2 │   StatefulSet
   └────┬────┘  gossip   └────┬────┘  gossip   └────┬────┘   (headless Service, :7946)
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              │
                     ┌────────▼────────┐
                     │   PostgreSQL    │   external; the only stateful dependency
                     └─────────────────┘
```

Every pod is identical, and any pod serves any request. There is no leader
election and no external coordination service. Correctness comes from
PostgreSQL: every transaction runs under `REPEATABLE READ` (snapshot
isolation), with first-committer-wins validation at commit. Gossip, encrypted
with the cluster's HMAC secret, provides peer awareness, and a request that
belongs to another pod's open transaction is proxied to that pod.

The chart renders:

| Object | Notes |
|---|---|
| `StatefulSet` | The cyoda pods. `podManagementPolicy: Parallel`, no volume claims, non-root, read-only root filesystem. `terminationGracePeriodSeconds: 390`. |
| `Service` | `ClusterIP` by default; ports `8080` (HTTP), `9090` (gRPC), `9091` (admin and metrics). |
| Headless `Service` | Gossip on `7946` TCP and UDP; gives each pod a stable DNS name. Publishes not-ready addresses so peers find each other before readiness. |
| `ConfigMap` | Non-secret settings, including all three bind addresses set to `0.0.0.0`, JWT mode, the PostgreSQL backend and the seed list. |
| Migration `Job` | Runs `cyoda migrate` as a pre-install and pre-upgrade hook. Mounts only the database DSN. |
| `HTTPRoute`, `GRPCRoute` | With `gateway.enabled=true` (the default). Attach to a Gateway you provide in `gateway.parentRefs`. |
| `Ingress` (HTTP and gRPC) | With `ingress.enabled=true` instead of the Gateway routes. |
| `NetworkPolicy` | On by default. Restricts the admin port to the namespaces you name and gossip to the chart's pods. |
| `PodDisruptionBudget` | On by default when more than one replica is possible; `minAvailable: 1`. |
| `Secret` (HMAC, metrics bearer) | Generated on first install unless you name existing Secrets. |
| `ServiceMonitor` | With `monitoring.serviceMonitor.enabled=true`. |
| `HorizontalPodAutoscaler` | With `autoscaling.enabled=true`. |
| `ServiceAccount` | With `serviceAccount.create=true` (the default). |

Cluster mode is always on. At one replica the pod runs as a cluster of one.
Each pod's `CYODA_NODE_ID` is its pod name (`cyoda-0`, `cyoda-1`, …), and its
`CYODA_NODE_ADDR` is its headless-Service DNS name on port 8080, so ids are
unique and fit the identity limit for any normal release name and namespace.

## Install

The chart requires Kubernetes 1.31 or later and is published to the Helm
repository `https://cyoda.github.io/cyoda-go` as `cyoda/cyoda`. A chart
release normally carries the version of the cyoda-go release it runs.

Create the namespace and the two Secrets the chart requires (the PostgreSQL
DSN and the JWT signing key) before you install. Keep secrets off the command
line:

```bash
kubectl create namespace cyoda

(umask 077; printf '%s' 'postgres://cyoda:secret@pg-host:5432/cyoda?sslmode=require' > pg-dsn)
kubectl create secret generic cyoda-pg -n cyoda --from-file=dsn=pg-dsn
rm pg-dsn

openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out signing.pem
kubectl create secret generic cyoda-jwt -n cyoda --from-file=signing-key.pem=signing.pem

helm repo add cyoda https://cyoda.github.io/cyoda-go
helm repo update
helm install cyoda cyoda/cyoda \
  --namespace cyoda \
  --set postgres.existingSecret=cyoda-pg \
  --set jwt.existingSecret=cyoda-jwt \
  --set "gateway.parentRefs[0].name=prod-gateway" \
  --set "gateway.parentRefs[0].namespace=gateway-system"
```

With `gateway.enabled=true`, the default, `gateway.parentRefs` is required:
an empty or missing list fails the install. On a cluster without Gateway API,
replace the two `gateway.parentRefs` lines with `--set gateway.enabled=false`
and use Ingress or the Service directly.

**Pin the image by digest.** The chart runs `image.repository:image.tag`, and
the tag defaults to the chart's app version. Tags can move, so for production
verify the release's image signature and set `image.tag` to
`<version>@<digest>`, for example `--set image.tag="0.9.0@$D"`. See
[Install](/run/install/).

<Aside type="caution" title="GitOps and dry runs">
The chart generates the HMAC and metrics-bearer Secrets with `lookup`, which
needs live cluster access. Rendered without it (`helm template`, `--dry-run`,
Argo CD), the chart fails unless `cluster.hmacSecret.existingSecret` and
`monitoring.metricsBearer.existingSecret` name Secrets you created. GitOps
deployments should always set both, so a reconcile never renders a new
cluster secret.
</Aside>

Rate-limit `/api/tenants/{tenant}/oauth/token` at the Gateway or Ingress; the
chart renders no rate limit. See [Helm values](/reference/helm/#token-endpoint-rate-limit).

## First admin token

The pods hold the signing key, so `cyoda token` run inside a pod signs the
first admin token. The binary in the image is `/cyoda`:

```bash
TOKEN=$(kubectl exec -n cyoda cyoda-0 -- /cyoda token --tenant acme)
```

Use it to create the M2M clients that applications and compute nodes use
(`POST /api/clients`). For platform operations, such as cluster status, sign
with `--tenant PLATFORM`. See [`cyoda help cli token`](/help/cli/token/) and
[Authenticating applications](/build/authenticating-applications/).

## Health, readiness and shutdown

The StatefulSet probes the admin port: liveness on `/livez`, readiness on
`/readyz` every 5 seconds. `/readyz` fails from the start of shutdown, so a
terminating pod leaves the Service at once, and after a recovered panic, which
takes the pod out of the Service within about 15 seconds. `/livez` keeps
passing in that case, so Kubernetes does not restart the pod into the same
panic: delete the pod to replace it. Peers route to it through gossip, not
the Service, so it keeps receiving forwarded work until you do.

The gRPC listener also serves the standard `grpc.health.v1.Health/Check`
without a token, for a `grpc` probe or a gRPC-aware load balancer.

A pod can take more than six minutes to shut down in the worst case, while
the scheduler lets a non-idempotent processor callout finish. The chart's
`terminationGracePeriodSeconds: 390` covers the default settings; raise it
with the settings it depends on. See [Cluster operations](/run/cluster-operations/#shutdown).

To check the cluster after an install, scale or upgrade:

```bash
TOKEN=$(kubectl exec -n cyoda cyoda-0 -- /cyoda token --tenant PLATFORM)
kubectl -n cyoda port-forward svc/cyoda 8080:http &
curl -s -H @- 'http://localhost:8080/api/platform/cluster?waitForNodes=3' \
  <<<"Authorization: Bearer $TOKEN"
```

A `200` means three pods are `UP` and `NORMAL` on one version. See
[Cluster status](/run/cluster-operations/#cluster-status).

## Upgrades

`helm upgrade` runs the migration Job, then rolls the StatefulSet one pod at a
time (`updateStrategy: RollingUpdate`). **That is safe only when the target
release's notes allow a rolling upgrade.** The upgrade from v0.8.4 to v0.9.0
is not rolling (see the [v0.9.0 release notes](/releases/v0-9-0/)). When the
notes do not allow it, scale to zero first:

```bash
# 1. Stop every pod and wait until none are left (kubectl reports
#    "no matching resources" if they are already gone).
kubectl -n cyoda scale statefulset cyoda --replicas=0
kubectl -n cyoda wait --for=delete pod -l 'app.kubernetes.io/instance=cyoda,statefulset.kubernetes.io/pod-name' --timeout=420s

# 2. Upgrade: the migration Job runs first, then the pods start on the new version.
helm repo update
helm upgrade cyoda cyoda/cyoda --namespace cyoda --reset-then-reuse-values --version 0.9.0

# 3. Wait for the pods, then check cluster status (above).
kubectl -n cyoda rollout status statefulset cyoda
```

`helm upgrade` sets the StatefulSet back to `replicas`. With
`autoscaling.enabled=true`, the chart leaves the replica count to the
HorizontalPodAutoscaler, which does not scale a workload up from zero: scale
it back with `kubectl scale` after the upgrade.

`--reset-then-reuse-values` keeps the values you set and takes the new chart's
defaults for the rest; `--reuse-values` would carry the old chart's full value
set and miss values the new chart adds.

**Migrations.** The migration Job runs `cyoda migrate` with its default
5-minute timeout, inside `migrate.activeDeadlineSeconds` (default `600`). Some
migrations block writers for a time that grows with the size of your tables
(see [Storage engines](/run/storage-engines/#migrations-and-maintenance-windows)).
On a large database, either raise `migrate.activeDeadlineSeconds`, or run
`cyoda migrate --timeout <duration>` with the new image against the database
while the cluster is at zero, before `helm upgrade`; the Job then has nothing
left to do. A Job killed in the middle of a migration leaves the schema marked
dirty, which needs manual recovery (see [`cyoda help cli migrate`](/help/cli/migrate/)).
If the Job fails, Helm does not move on to the new pods; read its log with
`kubectl logs -n cyoda job/cyoda-migrate-<revision>`.

Read the release notes before every upgrade, and run the [Cluster
operations](/run/cluster-operations/#upgrades) checklist.

## Backup and restore

Back up PostgreSQL with standard tooling: `pg_dump`, continuous WAL archiving,
or your provider's snapshots. The pods hold no data. Back up the Secrets too:
the JWT signing key (`jwt.existingSecret`), and the HMAC Secret if you manage
it yourself. The signing key signs every token cyoda-go issues and is the root
key for the issued key pairs; a replaced signing key retires them and every
token cyoda-go signed. The HMAC secret can be regenerated, with a full stop of
the cluster.

## Sizing

Reads scale across pods; writes go through the single PostgreSQL primary,
which bounds write throughput. The usual range is three pods for high
availability up to about ten, where the PostgreSQL connection budget becomes
the limit: each pod opens up to 44 connections at the default pool sizes
(25 main, 10 scheduler, 1 heartbeat, 8 model). Size `max_connections` for the
largest replica count you allow, including an autoscaler's `maxReplicas`. See
[Cluster operations](/run/cluster-operations/#postgresql-connection-budget).

The default pod resources are a request of `100m` CPU and `256Mi` memory and a
limit of `1000m` and `512Mi`. Measure your workload and set `resources`
accordingly.

For write volumes beyond a single PostgreSQL primary, commercial storage
backends are available; contact Cyoda.

## Observability

- **Metrics.** `/metrics` on port 9091 requires a bearer token: the chart sets
  `CYODA_METRICS_REQUIRE_AUTH=true` and generates the bearer Secret unless you
  name one. With `monitoring.serviceMonitor.enabled=true`, the chart renders a
  Prometheus Operator `ServiceMonitor` that reads the bearer from that Secret.
  The NetworkPolicy admits port 9091 only from the namespaces in
  `networkPolicy.metricsFromNamespaces` (default: `monitoring`).
- **Tracing.** Set the OpenTelemetry variables through `extraEnv`, for
  example `CYODA_OTEL_ENABLED` and `OTEL_EXPORTER_OTLP_ENDPOINT`. Pass
  `true`, `false` and numbers with `--set-string`: the chart's schema accepts
  only strings in `extraEnv[].value`.
- **Log level and sampling** can be changed at runtime per pod through
  `/api/admin/log-level` and `/api/admin/trace-sampler`, with a platform
  operator token. See [`cyoda help admin`](/help/admin/).

See [`cyoda help telemetry`](/help/telemetry/) for the instruments.
