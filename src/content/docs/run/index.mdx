Every packaging runs the same cyoda-go binary with the same application
contract and the same workflow semantics. What changes is durability, fault
tolerance and operational cost. Pick the packaging by what you need to
operate, not by what your application needs to do.

Start with [Install](/run/install/): every packaging begins with a verified
binary or a container image pinned by digest.

## Pick your packaging

|                  | In-memory | SQLite        | PostgreSQL       |
|------------------|-----------|---------------|------------------|
| **Desktop**      | ✓         | ✓ *(default)* |                  |
| **Docker**       | ✓         | ✓             | ✓                |
| **Kubernetes**   |           |               | ✓ *(production)* |

Multi-node clusters run on PostgreSQL only. For per-engine durability, fault
tolerance and deployment scope, see [Storage engines](/run/storage-engines/).
Commercial storage backends are also available; for those, contact Cyoda.

## When to pick what

- **[Desktop](/run/desktop/)** — a single binary on a laptop or a small
  server. In-memory for tests; SQLite as the default durable store. Right for
  development, edge and small single-node deployments.
- **[Docker](/run/docker/)** — the same binary in a container. Use it for
  compositions with other services, local PostgreSQL runs and CI pipelines.
- **[Kubernetes](/run/kubernetes/)** — the production packaging for
  self-hosted clusters: a StatefulSet of identical cyoda-go pods with
  PostgreSQL as the only stateful dependency, deployed with the Helm chart
  that ships with cyoda-go.

[Cluster operations](/run/cluster-operations/) covers what applies to every
multi-node deployment, whatever the packaging: node ids, bind addresses,
cluster status, health checks, shutdown timing, the PostgreSQL connection
budget and upgrades.

## Moving between packagings

The application does not change when you move. Start on Desktop, move to a
container when integration demands it, and cluster on Kubernetes when
availability or load demands it. The entity, workflow and API contracts are
the same at every step.

See [Digital twins and the growth path](/concepts/digital-twins-and-growth-path/)
for the decision framework.
